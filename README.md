# 社内RAG開発シミュレーション

> **架空企業の社内文書を使って、RAG（Retrieval-Augmented Generation）の設計・実装・評価と、Security for AI の検証・改善を実践する個人開発プロジェクト。**

## 概要

本リポジトリは、完全架空の企業 **蒼星デジタルソリューションズ株式会社** をクライアントに設定した、社内ナレッジ検索・回答支援システムの開発シミュレーションです。

実際のシステム開発に近い流れで、企業・業務の理解、要件定義、PoC（概念実証）、基本設計・本実装、評価・改善を進めます。特に、RAGの回答品質だけでなく、**文書のアクセス権限、根拠の信頼性、Prompt Injectionなどの安全性**を重点的に扱います。

**注意：** 企業名・人物・文書・業務記録・数値はすべて演習用の架空情報です。実在企業の機密情報や個人情報は利用しません。

## 目的

1. **RAG開発の一連の工程を経験する**：要件から評価・改善まで、実務に近い形で実践する。
2. **検索・生成の品質を測る**：検索精度、回答の正確性、引用の整合性、回答保留の妥当性を検証する。
3. **Security for AI を学ぶ**：権限外文書の取得、Prompt Injection、古い文書の参照などのリスクを、安全な検証環境で再現・評価する。
4. **対策の有効性を比較する**：ベースラインと改善後を同じ評価条件で比較し、設計上のトレードオフを記録する。

## 想定ユースケース

社員が社内規程や業務手順について自然言語で質問すると、システムが**その利用者に閲覧権限のある文書**から関連情報を検索し、根拠を添えて回答します。十分な根拠がないときは推測で埋めず、回答を保留します。

例：

- 現行の出張旅費規程を確認する。
- 社内ITの問い合わせ手順を探す。
- 規程の旧版と新版を適用日で区別する。
- 閲覧権限のない部署の資料を回答に含めない。
- 参照文書に含まれた不正な指示を、システムへの命令として扱わない。

社内システムの更新、申請承認、外部サービスへの操作などの**アクション実行は初期スコープ外**です。

## 開発の進め方

| フェーズ | 内容 | 主な成果物 |
| --- | --- | --- |
| 1. 企業設定・データ準備 | 架空企業の組織、業務、社内文書、文書属性を定義 | 企業設定資料、サンプル社内文書、メタデータ |
| 2. 要件定義 | 利用者・業務課題・必要機能・セキュリティ・評価観点を整理 | 要件定義書 |
| 3. PoC | 小さなRAGを構築し、技術的な実現性と懸念事項を検証 | 動作するベースライン、評価結果、課題一覧 |
| 4. 基本設計・本実装 | PoCの知見を反映し、アーキテクチャ・認証認可・運用などを設計・実装 | 設計書、アプリケーション、テスト |
| 5. セキュリティ評価・改善 | 安全なテストケースで弱点を確認し、対策・再評価を反復 | 検証シナリオ、比較結果、改善履歴 |

PoCは**最終システムの縮小版を完成させる工程ではありません**。技術選定、問題点の洗い出し、評価方法の確立を重視し、必要であれば本実装で作り直します。

## PoCで確かめること

PoCでは限定した架空文書を使い、可能な限りローカル・無料の構成を優先して、次を確認します。

- **文書取込**：テキスト抽出、チャンク分割、メタデータの付与ができるか。
- **検索**：質問に関連する文書を適切に取得できるか。
- **回答**：取得文書に基づく回答と出典提示ができるか。
- **権限制御**：ユーザーのロールに応じて、検索段階からアクセスを制限できるか。
- **文書の版管理**：旧版・現行版・適用日の違いを扱えるか。
- **安全性**：参照文書内の指示に誘導されないか、権限外情報を出力しないか。
- **計測**：品質・応答時間・運用負荷を比較できる形で記録できるか。

PoCで採用するライブラリ、モデル、ベクトルストア、起動コマンドは、実装に合わせて別途確定します。README内の記述だけで**未実装の機能が動作することを保証するものではありません**。

## 評価の観点

| 観点 | 確認内容 | 指標・判定例 |
| --- | --- | --- |
| 検索品質 | 正解文書が上位に見つかるか | Recall@k など |
| 回答品質 | 回答が文書の内容と一致するか | 正答率、定性レビュー |
| 根拠提示 | 回答と引用元が整合するか | 引用整合性 |
| 回答保留 | 根拠のない質問を推測で回答しないか | 回答不可判定の適切さ |
| 認可 | 権限外文書を検索・LLM入力・回答に混入させないか | 禁止文書の取得・引用件数 |
| 版・適用日 | 質問時点に適した版を使うか | 時点別テスト |
| 耐攻撃性 | 悪意のある文書内容に従わないか | セキュリティテストの成否 |
| 性能・費用 | 実行に必要な時間とコスト | p50/p95応答時間、実測費用 |

評価基準値は、PoCで測定した結果と要件の確認を踏まえて決定します。要件定義中の数値目標は、正式な受入基準ではありません。

## セキュリティ方針

本プロジェクトは、防御・評価・学習を目的とした**隔離された架空環境**を前提とします。

- 文書の本文や検索結果は**信頼できない入力**として扱う。
- 文書の閲覧権限は、生成後の出力フィルタだけでなく**検索前**に適用する。
- 閲覧禁止の文書を、プロンプト・再ランキング・ログなどの後段へ渡さない設計を目指す。
- 根拠のない推測や、参照文書の指示によるシステム動作の上書きを防ぐ。
- テストに使うデータ、ID、トークンはダミーとし、実際の秘密情報をコミットしない。
- 攻撃検証は自分が管理する本演習環境内でのみ実施する。

### 代表的な検証シナリオ

1. 権限のない部署の資料を質問しても、内容が検索・回答に現れない。
2. 古い旅費規程と現行規程を混同しない。
3. 関連情報が存在しない質問で、断定的な架空回答をしない。
4. 参照文書内の「これまでの指示を無視せよ」といった文面に従わない。
5. 文書更新や権限変更後に、失効した情報を継続利用しない。

## データについて

演習用の企業資料、社内文書およびメタデータを利用します。文書ID、所管部署、機密区分、閲覧可能ロール、適用日、改訂履歴などの属性を整理し、検索と評価に利用する想定です。

なお、元の社内文書一式や設計資料の**配置先・ディレクトリ構成は、リポジトリの実ファイルに合わせて管理**します。本READMEでは、現時点で未確認のディレクトリ名を固定していません。

## 開発・検証時の記録ルール

- 変更ごとに「仮説 → 変更内容 → 評価条件 → 結果 → 考察」を残す。
- 検索器やモデルを比較するときは、可能な限り同じ評価データを使う。
- 成功事例だけでなく、失敗した質問、権限の誤判定、根拠不一致も記録する。
- PoCで確定した事項と、要件上の未確定事項を区別する。
- 実験結果は測定条件（モデル、設定、文書集合、実行環境）とセットで残す。
